# سند اصلی پروژه فروشگاه

> این فایل مرجع اصلی شناخت پروژه، تصمیم‌های فنی و میزان پیشرفت کلی است. قبل از هر تغییر مهم، این سند و فایل `MANAGER.md` را بررسی و در صورت نیاز به‌روزرسانی کن.

## ۱. معرفی پروژه

هدف، ساخت یک فروشگاه اینترنتی با Laravel است که ابتدا به‌صورت محلی توسعه داده می‌شود و در نهایت روی هاست اشتراکی مستقر خواهد شد.

### فناوری‌ها و معماری

- Backend: Laravel
- Frontend: Vue 3 + TypeScript
- ارتباط صفحات و سرور: Inertia.js
- احراز هویت: Laravel Fortify
- CSS: Tailwind CSS
- Build و توسعه فرانت‌اند: Vite Plus
- پایگاه داده محیط توسعه: MariaDB
- محیط توسعه فعلی: Windows 11 و XAMPP برای MariaDB

### قابلیت‌های پایه فعلی

- ثبت‌نام کاربران
- ورود با ایمیل و رمز عبور
- تأیید ایمیل
- تأیید مجدد رمز عبور برای عملیات حساس

ورود با شماره موبایل و کد یک‌بارمصرف (OTP) برای آینده در نظر گرفته شده است و تا زمان ثبت آن به‌عنوان وظیفه، نباید پیاده‌سازی شود. احراز هویت دومرحله‌ای و Passkeys نیز فعلاً در محدوده کار نیستند.

## ۲. نسخه‌های مبنای فنی

**اصل مهم:** توسعه و تغییرات پروژه باید با نسخه‌های ثبت‌شده در این بخش و وابستگی‌های قفل‌شده در فایل‌های `composer.lock` و `package-lock.json` سازگار باشد. نسخه هیچ ابزار یا پکیجی بدون هماهنگی و تأیید تغییر نکند. قبل از ارتقا، اثر آن بر کل پروژه و امکان استقرار روی هاست بررسی شود.

### محدودیت نسخه‌ها و مرجع تشخیص

- نسخه‌های دقیق پکیج‌های PHP از `composer.lock` و پکیج‌های JavaScript از `package-lock.json` خوانده می‌شوند.
- فایل‌های lock باید همراه تغییرات وابستگی‌ها حفظ و در Git ثبت شوند.
- مقادیر نسخه در این سند، مبنای محیط فعلی هستند؛ اگر وضعیت واقعی محیط تغییر کرد، ابتدا علت و اثر آن بررسی و سپس با تأیید، این سند اصلاح شود.
- شرط PHP در `composer.json` برابر `^8.3` است؛ نسخه محیط توسعه فعلی 8.5.0 است.
- برای استقرار، نسخه PHP و پایگاه داده هاست باید با پروژه سازگار باشد. هیچ فرضی درباره امکانات SSH یا Node.js روی هاست اشتراکی نداریم؛ خروجی build و وابستگی‌های لازم باید پیش از استقرار آماده شوند.

## ۳. ساختار شاخه‌های Git

فقط دو شاخه اصلی نگهداری می‌شوند:

- `main`: نسخه پایدار و آماده استقرار.
- `dev`: شاخه اصلی توسعه، آزمایش و تکمیل قابلیت‌ها.

کدنویسی روزمره روی `dev` انجام می‌شود. پس از بررسی و اطمینان از پایداری، تغییرات `dev` به `main` منتقل می‌شوند. شاخه‌های متعدد برای هر قابلیت ایجاد نمی‌کنیم، مگر اینکه بعداً دلیل ضروری و مورد توافقی وجود داشته باشد.

## ۴. ثبت و محاسبه پیشرفت پروژه

فهرست وظایف فعال در فایل `MANAGER.md` نگهداری می‌شود. وظایف انجام‌شده از فهرست فعال حذف می‌شوند، اما تعداد تجمعی آن‌ها در همین بخش حفظ می‌شود تا سابقه پیشرفت از بین نرود.

### وضعیت فعلی

| شاخص | تعداد |
|---|---:|
| وظایف تکمیل‌شده تجمعی | 0 |
| وظایف در حال انجام | 0 |
| وظایف در انتظار شروع | 0 |
| مجموع وظایف تعریف‌شده تا امروز | 0 |
| پیشرفت | هنوز وظیفه‌ای ثبت نشده است |

### روش محاسبه

`مجموع وظایف تعریف‌شده = وظایف تکمیل‌شده تجمعی + وظایف فعال در MANAGER.md`

`درصد پیشرفت = (تعداد وظایف تکمیل‌شده تجمعی ÷ مجموع وظایف تعریف‌شده) × 100`

مثلاً اگر ۳ وظیفه از مجموع ۵ وظیفه تکمیل شده باشد، پیشرفت ۶۰٪ است. اگر وظیفه جدیدی تعریف شود، به مجموع اضافه می‌شود و درصد بر اساس مجموع جدید محاسبه خواهد شد.

هنگام تکمیل هر وظیفه:
1. آن را از فهرست فعال در `MANAGER.md` حذف کن.
2. شمارنده «وظایف تکمیل‌شده تجمعی» را در همین فایل یک واحد افزایش بده.
3. شمارنده‌های وضعیت و درصد پیشرفت را به‌روز کن.

به این ترتیب فهرست Manager فقط کارهای باز و در حال انجام را نشان می‌دهد و تاریخچه پیشرفت کلی با حذف وظایف از بین نمی‌رود.

## ۵. قواعد همکاری و نگهداری اسناد

- پیش از شروع هر کار، این سند و `MANAGER.md` بررسی شوند.
- هر درخواست یا ایده جدید ابتدا به‌عنوان وظیفه در Manager ثبت شود؛ سپس توسعه آغاز شود.
- کارهای در حال انجام و کارهای منتظر شروع باید از هم قابل تشخیص باشند.
- پس از پایان هر کار، وضعیت اسناد و شمارنده پیشرفت در همان تغییر به‌روزرسانی شوند.
- تصمیم‌های فنی مهم، تغییر معماری و تغییر نسخه‌ها باید در این سند ثبت شوند.
- قابلیت‌هایی که هنوز درخواست یا تأیید نشده‌اند، خودسرانه وارد پروژه نشوند.
