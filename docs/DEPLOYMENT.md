# راهنمای نیازمندی‌ها و استقرار

این راهنما برای آماده‌سازی پروژه Laravel 13 جهت استقرار روی هاست اشتراکی نوشته شده است. تا زمانی که مشخصات هاست واقعی بررسی نشده، این سند به معنی تأیید سازگاری با یک شرکت میزبانی خاص نیست.

## ۱. حداقل نیازمندی‌های فنی

### PHP

- حداقل نسخه موردنیاز این پروژه: PHP 8.4 (به‌دلیل وابستگی‌های قفل‌شده فعلی؛ با وجود حداقل عمومی پایین‌تر Laravel 13)
- نسخه PHP هاست باید 8.4 یا بالاتر و در محدوده نسخه‌های پشتیبانی‌شده وابستگی‌های قفل‌شده پروژه باشد.
- افزونه‌های PHP موردنیاز:
    - Ctype
    - cURL
    - DOM
    - Fileinfo
    - Filter
    - Hash
    - Mbstring
    - OpenSSL
    - PCRE
    - PDO
    - Session
    - Tokenizer
    - XML
- برای اتصال به MariaDB/MySQL، افزونه PDO MySQL نیز باید فعال باشد.

### پایگاه داده

Laravel 13 به‌صورت رسمی از این حداقل نسخه‌ها پشتیبانی می‌کند:

- MariaDB 10.3 یا جدیدتر
- MySQL 5.7 یا جدیدتر

نسخه MariaDB محیط توسعه فعلی پروژه 10.4.32 است و از نظر حداقل نسخه اعلام‌شده Laravel مناسب است. نسخه دقیق سرور هاست باید پیش از خرید یا استقرار بررسی شود.

### وب‌سرور و فایل‌ها

- وب‌سرور باید درخواست‌های برنامه را به `public/index.php` هدایت کند.
- Document Root دامنه باید مستقیماً روی پوشه `public` پروژه تنظیم شود.
- فایل‌های ریشه پروژه، از جمله `.env`، نباید از وب قابل دسترسی باشند.
- پوشه‌های `storage` و `bootstrap/cache` باید برای کاربر اجرای PHP قابل نوشتن باشند.
- برای نمایش تصاویر محصولات، disk عمومی باید قابل نوشتن باشد و مسیر `public/storage` به `storage/app/public` متصل شود.
- سایت باید با HTTPS و گواهی معتبر اجرا شود.

## ۲. تنظیمات محیط Production

مقادیر زیر باید در فایل محیطی خصوصی سرور تنظیم شوند. هیچ‌وقت فایل واقعی `.env` را در Git ثبت نکنید.

مقادیر کلیدی:

```dotenv
APP_ENV=production
APP_DEBUG=false
APP_URL=https://example.com

DB_CONNECTION=mysql
DB_HOST=127.0.0.1
DB_PORT=3306
DB_DATABASE=database_name
DB_USERNAME=database_user
DB_PASSWORD=strong_database_password

SESSION_DRIVER=database
SESSION_SECURE_COOKIE=true
SESSION_HTTP_ONLY=true
SESSION_SAME_SITE=lax

SANCTUM_STATEFUL_DOMAINS=example.com
```

- دامنه واقعی را جایگزین `example.com` کنید.
- مقدار `SANCTUM_STATEFUL_DOMAINS` فقط شامل hostname و در صورت نیاز port است؛ scheme مانند `https://` را وارد نکنید.
- اگر سایت با چند hostname مانند دامنه اصلی و `www` قابل دسترسی است، همه hostnameهایی که واقعاً برای SPA استفاده می‌شوند باید با کاما ثبت شوند.
- برای نصب تک‌دامنه‌ای، متغیر `SESSION_DOMAIN` را معمولاً خالی نگه دارید تا Cookie به همان host محدود بماند.
- اگر بعداً Frontend و API روی زیردامنه‌های جدا قرار گرفتند، تنظیمات Cookie، CORS و دامنه نشست باید جداگانه بازبینی شوند؛ این حالت جزو استقرار اولیه تک‌دامنه‌ای نیست.
- `APP_KEY` باید روی سرور با دستور `php artisan key:generate` ایجاد شود و پس از استقرار تغییر نکند.

## ۳. آماده‌سازی و Build

در محیطی با نسخه PHP سازگار و دسترسی به Composer:

```bash
composer install --no-dev --optimize-autoloader
npm ci
npm run build
```

- خروجی build فرانت‌اند، به‌ویژه `public/build` و manifest آن، باید روی سرور منتشر شود.
- در صورت نبود Node.js روی هاست، build را در محیط توسعه یا CI انجام دهید و خروجی تولیدشده را همراه انتشار برنامه منتقل کنید.
- فایل‌های `composer.lock` و `package-lock.json` باید همراه نسخه منتشرشده باشند.
- نسخه‌های وابستگی را روی سرور با `composer update` یا `npm update` تغییر ندهید.

## ۴. ترتیب اولیه استقرار

1. از پایگاه داده و فایل‌های نسخه قبلی پشتیبان تهیه کنید.
2. فایل‌های برنامه را خارج از Document Root عمومی قرار دهید و Document Root را روی پوشه `public` تنظیم کنید.
3. فایل محیطی Production و اطلاعات اتصال دیتابیس را تنظیم کنید.
4. وابستگی‌های PHP را نصب یا نسخه build‌شده و سازگار آن‌ها را منتقل کنید.
5. خروجی Frontend را در `public/build` قرار دهید.
6. دسترسی نوشتن `storage` و `bootstrap/cache` را بررسی کنید.
7. پیوند فایل‌های عمومی را با دستور `php artisan storage:link` بسازید و دسترسی نوشتن `storage/app/public` را بررسی کنید.
8. migrationها را با دستور زیر اجرا کنید:

    ```bash
    php artisan migrate --force
    ```

9. پس از اطمینان از تنظیمات Production، Cacheهای بهینه‌سازی را بسازید:

    ```bash
    php artisan optimize
    ```

10. مسیرهای سلامت را بررسی کنید:
    - `/up`
    - `/api/v1/health`
11. ثبت‌نام، ورود، تأیید ایمیل، بازیابی رمز و نشست API را در محیط HTTPS آزمایش کنید.

از اجرای `migrate:fresh` یا هر دستور حذف داده در Production خودداری کنید.

## ۵. احراز هویت SPA و Sanctum

معماری فعلی برای Frontend و Backend هم‌دامنه از نشست Cookie استفاده می‌کند؛ برای SPA خود پروژه نیازی به صدور Personal Access Token نیست.

ترتیب درخواست‌های کلاینت:

1. درخواست GET به `/sanctum/csrf-cookie` برای دریافت Cookie با نام `XSRF-TOKEN`.
2. درخواست POST به `/login` با `Accept: application/json` و اطلاعات ورود.
3. ارسال Cookie نشست در درخواست‌های بعدی.
4. ارسال مقدار URL-decoded کوکی `XSRF-TOKEN` در هدر `X-XSRF-TOKEN` برای درخواست‌های تغییردهنده وضعیت.
5. استفاده از `GET /api/v1/me` برای دریافت اطلاعات حساب واردشده.
6. استفاده از `POST /logout` برای خروج.

درخواست‌های SPA باید هدر `Origin` یا `Referer` معتبر داشته باشند و hostname آن‌ها در فهرست stateful Sanctum قرار گرفته باشد. برای کلاینت‌های مبتنی بر Axios، گزینه‌های `withCredentials` و `withXSRFToken` باید فعال شوند؛ در سایر کلاینت‌ها رفتار معادل پیاده‌سازی شود.

در استقرار تک‌دامنه‌ای نیازی به فعال‌کردن CORS برای ارتباط داخلی همان origin نیست. اگر معماری به چند origin تغییر کرد، CORS و Cookieها باید با دامنه‌های دقیق و مجاز پیکربندی شوند.

## ۶. مدیریت امن دسترسی مدیر

پس از ثبت‌نام کاربر موردنظر، دسترسی مدیر فقط از طریق محیط CLI و با حساب دارای دسترسی مدیریتی به سرور تغییر داده شود:

```bash
php artisan app:admin:set admin@example.com grant
php artisan app:admin:set admin@example.com revoke
```

- ایمیل باید متعلق به یک کاربر موجود باشد.
- فرمان قبل از هر تغییر، تأیید تعاملی می‌خواهد.
- فرمان اجازه لغو دسترسی آخرین مدیر را نمی‌دهد.
- این عملیات را از طریق endpoint عمومی وب یا با قابل‌mass-assign کردن `is_admin` انجام ندهید.

## ۷. کارهای وابسته به امکانات هاست

پیش از انتخاب هاست، این موارد را از شرکت ارائه‌دهنده بپرسید:

- نسخه PHP و امکان انتخاب نسخه برای دامنه
- فعال بودن افزونه‌های موردنیاز PHP و PDO MySQL
- نسخه MariaDB یا MySQL
- امکان تنظیم Document Root روی پوشه `public`
- امکان اجرای Composer یا روش مجاز انتقال وابستگی‌های نصب‌شده
- امکان اجرای Artisan از SSH یا Cron
- امکان تعریف Cron Job برای صف‌ها و زمان‌بندی‌های آینده
- محدودیت حجم فایل، حافظه PHP، زمان اجرای درخواست و تعداد پردازش‌ها
- امکان استفاده از HTTPS و تمدید خودکار گواهی

اگر SSH در دسترس نباشد، روش امن اجرای migration، cache و سایر دستورات مدیریتی باید متناسب با امکانات همان هاست طراحی شود؛ اجرای دستورات مدیریتی از مسیر عمومی وب بدون احراز هویت و کنترل دسترسی قابل قبول نیست.

## ۸. مواردی که هنوز باید در استقرار واقعی آزمایش شوند

- نسخه PHP و افزونه‌های هاست واقعی
- سازگاری نسخه دقیق MariaDB/MySQL هاست
- اجرای migrationها روی دیتابیس خالی و دیتابیس دارای داده
- مسیر صحیح Document Root و جلوگیری از دسترسی عمومی به فایل‌های خصوصی
- مجوزهای نوشتن پوشه‌ها
- کارکرد Cookie امن و CSRF روی HTTPS
- تنظیمات ایمیل برای تأیید ایمیل و بازیابی رمز
- اجرای Queue و Cron در محدودیت‌های هاست
- پشتیبان‌گیری و بازیابی قبل از ارتقا

**وضعیت:** این سند چک‌لیست و معیار ارزیابی است؛ استقرار واقعی هنوز انجام نشده و سازگاری هاست مشخصی تأیید نشده است.
